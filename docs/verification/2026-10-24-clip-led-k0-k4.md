## 2. K0 — audit and baseline

Two defects were found by re-running the 13-second hybrid fixture. Both were reproduced before fixing.

**Defect 1 — `CaptionPerformer` measured against the wrong box in a scaled preview.** `--story=video-phase-2-hybrid-short--short` (without `kmExport=1`) renders the film inside a `transform: scale(0.3)` preview. The component read its lane size from `getBoundingClientRect()`, which includes the transform, while it measured text at the unscaled font size. The lane was therefore 0.3× too narrow for the text it was sizing. Frame 292 then reported `caption-no-room` for "So you are told: stop three of twelve." and the export stopped there.
- Fix: `registry/visual/caption-performer.tsx` uses `offsetWidth`/`offsetHeight` (layout size), so the lane and the measured text share units under a CSS transform.
- Check after the fix: the scaled preview reports no `caption-no-room` at frames 292, 300, 320 and 330. The only remaining diagnostics are two authored warnings (`clip-upscaled`, `caption-hold-short`); they are not errors and are not hidden.

**Defect 2 — the `--story` export wrote a 324×576 file.** The exporter captured whatever the scaled preview drew, so the output was 0.3× the manifest size, and nothing checked it.
- Fix: `--story` now opens the story with `kmExport=1`, and every PNG's IHDR size is compared with the manifest before it is encoded. A mismatch stops the export with a message.

## 4. K4 — long-form export

### 4.1 What changed
- **No PNG spool.** Each capture is written to FFmpeg's stdin; `write()` waits for `drain`, so memory is bounded by one frame.
- **Verified before it counts.** Each output is probed with `ffprobe -count_frames`: codec, size, rate, decoded frame count, video duration and audio duration (audio tolerance 1.5 frames for AAC framing). Only a verified file is renamed onto `--output`.
- **Atomic output.** Encoding goes to `<output>.partial.mp4`. Failure or SIGINT/SIGTERM removes it; the previous output is never touched. Interrupts exit with 130/143.
- **Resumable segments (`--segmentSeconds=<n>`).** The range is split into verified video segments in `<output>.segments/`, joined with `-c copy`, and audio is muxed once from the full mix, so no AAC priming is added per segment. A rerun reuses every segment that still verifies, and `key.json` resets the folder when the URL or output geometry changes.
- **Segment retry.** A segment that fails capture or verification is re-rendered from a fresh page, up to three attempts. Earlier segments remain.
- **Size guard.** Every PNG's IHDR size is checked against the manifest.

The default single-pass mode still exists; `--segmentSeconds` opts in.

### 4.2 Behaviour checks (new runs)
- **Interrupt and resume:** 10 s range, 2 s segments, SIGTERM after two segments. Exit 143; no `.partial` file; two verified segments kept. Rerun: "Reused" for both, three rendered, output verified. Two independent interrupt-and-resume trials gave the same output (sha256 `7052af8b…`). I did not run an uninterrupted segmented encode of this range.
- **Segment joins vs single pass:** the same 10 s range encoded single-pass and segmented: 300 frames each, per-frame PSNR minimum 54.6 dB, mean 57.6 dB. These two encodes differ bit-for-bit because each segment starts with its own keyframe; content is the same. Joins across real film transitions are **not** tested.
- **Smoke, static build:** the same 1-second export gives the same sha256 on the dev server and on a static Storybook build.

### 4.5 Failures seen during this work
Three runs on the dev server failed before the final one, and a later 900-frame control run passed. No failed run wrote an output file. Partial files were removed; the segmented run kept its verified segments, as designed. The causes matter:
- Three runs on the **dev server** failed with `Element is not attached to the DOM`, `Cannot find context with specified id`, or a 30 s screenshot timeout. Each followed a file change in the repository (`package.json`, a docs file). A deliberate test (touching a docs file 25 s into a 600-frame dev-server export) reproduced a failure, and a 900-frame dev-server run with no file changes succeeded. The likely cause is the dev server's reload behaviour, not the exporter's own code. This is an inference from three incidents and one control run; it was not isolated further.
- The fix used for the final run is a **static build**, which has no file watcher. Its first 1-second smoke test matches the dev-server output byte-for-byte.
- Segment retry (§4.1) is designed to recover from transient page loss. It has not been exercised against a real page crash.
